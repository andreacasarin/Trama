- Indexing performance is a correctness invariant: every faster path must preserve occurrences, generation fencing, semantic convergence, atomic promotion, and coherent publication. SQLite owns bounded staged relational mutation, coverage, promotion, cleanup, and active FTS; JavaScript owns vault I/O, Markdown parsing/chunking, exact-input hashing, provider calls, and vector transfer. Current centroids stay query-time JavaScript by deliberate choice because indexing evidence did not justify storing them.
- Lifecycle performance comparisons use a versioned stable contract: freeze exact input Markdown, paths, mutations, queries, and provider identities separately from expected observable outputs, then run the same inputs across implementations. Intended output or chunking changes require a new expected-output version and cannot be presented as equivalent-output speedups. Core metrics and correctness remain independent of optional internal RPC or phase diagnostics.
- Full recovery is one vault scan followed by dirty-journal drain; scoped automatic work touches only changed eligible paths. Dense-note staging adaptively flushes complete notes, using TEMP oversized single-note slices with atomic promotion: singleton batches are <=16 MiB, including exactly 8 MiB, while multi-note batches stay <=8 MiB. Generation tokens and mutation receipts keep global state out of batch paths and account for applied or discarded mutations. Semantic prepare/commit is set-based and bounded, with complete compatible coverage required before affected-note promotion.
- Manual and automatic indexing share one operation lease and the same Stop semantics: Stop waits for the active operation, releases cleanly, and suppresses immediate retry. The coupled runtime schema/protocol/build identity is v9 with fresh incompatible-database reset; summary counts derive from authoritative relational tables rather than persisted lexical, semantic, or embedding-input revision counters. Semantic lag remains searchable through the prior head until atomic promotion, and publication validates one coherent active-head/cache set. Publication inspection is maintenance-reserved and cannot replace the live database during an active lexical run; a non-newer incompatible synchronized snapshot is replaced from the converged local index, while a newer schema remains untouched and requires a plugin update.
- `MutableSqliteDatabase` is the Worker-facing aggregate rather than the owner of every SQL concern. Shared connection and runtime configuration live in `sqlite/core.ts`; state/schema checks, bounded lexical batches, oversized lexical staging, lexical-run reconciliation, semantic prepare/commit, retrieval, and publication validation are separate acyclic modules. The façade owns construction and database closure, while the lexical run registry remains Worker-local and shared only by the three lexical modules.
- `IndexManager` is the stable public façade and composition root. Its acyclic `index/manager` services give client/state/maintenance, the mutation journal, lexical snapshot and scoped orchestration, semantic preparation, publication, and retrieval one owner each. The façade preserves the existing import path and public behavior; no manager service imports the façade.
- `MaintenanceScheduler` is the sole maintenance lifecycle owner. It owns pending intent, adaptive 3→9→20 second quiet windows with a 60-second generation deadline, explicit precedence, one active lane, safe-boundary cancellation, suspension, publication/adoption serialization, displayed activity, and permanent asynchronous disposal. Lexical, semantic, publication, and adoption remain narrow executors; there are no channel controllers, retry timers, executor wakeup callbacks, quit publication, or duplicate operation leases.
- Explicit Update converges finite lexical passes, configured semantic batches, and publication; Rebuild performs fresh lexical construction, clears configured semantic vectors once, resumes batches incrementally, and publishes only after convergence. With no embedding model, semantic work is skipped without a network request. Stop preserves pending intent and lets a started publication/adoption fence settle. Failures preserve committed data, display the error, suspend automatic work, and create no automatic retry.
- Settings schema 5 is the only accepted settings schema. `automaticMaintenance` and `lente.automaticSearches` are independent opt-ins; automatic searches use a fixed 500 ms debounce. Automatic maintenance is normally the consent boundary for event-triggered note embeddings and publication; replacing an incompatible non-newer synchronized index is the disclosed exception and first converges the configured local index. Replacement verifies that the rejected synchronized file did not change during convergence, while newer schemas prompt a Community plugins update. Settings expose Update, Rebuild, Stop, and Check only. Settings loading remains network-silent.
- `TramaPlugin` remains the Obsidian lifecycle composition root, while `RuntimeComposition` constructs the narrow runtime. Recomposition detaches callbacks, awaits startup load and scheduler disposal before invalidating/disposing the old manager, and transfers at most one dirty latch. Unload removes public references synchronously and terminates the captured index only after startup load and scheduler disposal settle.
- The SQLite protocol owns the single method tuple, types, limits, and safe errors; exhaustive request validation is a separate one-way consumer and every protocol method must be handled explicitly. Worker snapshot maintenance owns publication preparation, inspection, finalization, and atomic adoption. Hot SQL guarded by query-plan tests is production-owned so tests cannot drift from executed statements.
