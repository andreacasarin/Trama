- Indexing performance is a correctness invariant: every faster path must preserve occurrences, generation fencing, semantic convergence, atomic promotion, and coherent publication. SQLite owns bounded staged relational mutation, coverage, promotion, cleanup, and active FTS; JavaScript owns vault I/O, Markdown parsing/chunking, exact-input hashing, provider calls, and vector transfer. Current centroids stay query-time JavaScript by deliberate choice because indexing evidence did not justify storing them.
- Full recovery is one vault scan followed by dirty-journal drain; scoped automatic work touches only changed eligible paths. Dense-note staging adaptively flushes complete notes, using TEMP oversized single-note slices with atomic promotion: singleton batches are <=16 MiB, including exactly 8 MiB, while multi-note batches stay <=8 MiB. Generation tokens and mutation receipts keep global state out of batch paths and account for applied or discarded mutations. Semantic prepare/commit is set-based and bounded, with complete compatible coverage required before affected-note promotion.
- Manual and automatic indexing share one operation lease and the same Stop semantics: Stop waits for the active operation, releases cleanly, and suppresses immediate retry. The runtime is schema/protocol v8 with fresh incompatible-database reset; semantic lag remains searchable through the prior head until atomic promotion, and publication validates one coherent active-head/cache set. Publication inspection is maintenance-reserved and cannot replace the live database during an active lexical run.
- `MutableSqliteDatabase` is the Worker-facing aggregate rather than the owner of every SQL concern. Shared connection and runtime configuration live in `sqlite/core.ts`; state/schema checks, bounded lexical batches, oversized lexical staging, lexical-run reconciliation, semantic prepare/commit, retrieval, and publication validation are separate acyclic modules. The façade owns construction and database closure, while the lexical run registry remains Worker-local and shared only by the three lexical modules.
- `IndexManager` is the stable public façade and composition root. Its acyclic `index/manager` services give client/state/maintenance, the mutation journal, lexical snapshot and scoped orchestration, semantic preparation, publication, and retrieval one owner each. The façade preserves the existing import path and public behavior; no manager service imports the façade.
- `TramaPlugin` remains the Obsidian lifecycle and cross-channel composition root. Automatic lexical, semantic, and publication state is private to separate controllers and is observed through snapshots and narrow commands; startup recovery policy belongs to the lexical controller. Explicit index operations, model/view rebinding, SQLite bootstrap, runtime composition, vault event routing, UI registration, and scheduler status projection are separate acyclic modules. Channel controllers do not import one another and communicate only through the composition root's narrow ports.
- Automatic semantic intent remains owned by its controller across lexical, maintenance, lease, and publication blockers. Blocker clearing is event-driven through those narrow composition ports, with no polling or duplicate scheduler ownership; publication settlement callbacks run after maintenance release.
- The SQLite protocol owns the single method tuple, types, limits, and safe errors; exhaustive request validation is a separate one-way consumer and every protocol method must be handled explicitly. Worker snapshot maintenance owns publication preparation, inspection, finalization, and atomic adoption. Hot SQL guarded by query-plan tests is production-owned so tests cannot drift from executed statements. Index operation leases and the immutable status/progress model are independent of the status controller.
