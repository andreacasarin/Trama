# V1 implementation: LangChain and SQLite

This document describes the approved and implemented V1 architecture. The matching durable decision is recorded in [the note-index ADR](../.ai/adrs/langchain-sqlite-note-index.md).

## Scope

V1 is a complete rewrite around LangChain's vector-store and default Markdown-splitting interfaces, OpenAI embeddings, a native LangChain agent, tools validated with Zod, and native call limits. Obsidian adapters handle vault and plugin integration. This rewrite does not preserve the former application's APIs, schemas, ranking, settings, caches, or test goldens; it adds no backwards-compatibility layer, migrations, shims, or parallel indexes. The implementation keeps indexed-data filtering, grouping, ranking, and vector scoring in SQLite using native SQLite/WASM functions; JavaScript orchestrates bounded inputs and presents results.

Each vault's storage identity is created once at `.trama/note-v1/identity.json` as a version-1 random 32-byte token encoded in hex. Trama validates it on reload and uses it for the isolated OPFS database `trama-note-v2-<token>/notes.sqlite3`. The identity keeps the same vault namespace stable across reloads; copying the identity file copies that namespace. There is no shared-storage fallback. The SQLite database is initialized in the worker before RPC requests are handled.

The vector store persists chunk vectors, normalized note centroids, and lexical search data without raw Markdown bodies. LangChain's native index lifecycle owns content and metadata hashes, record UIDs, skip/refresh decisions, and stale-record cleanup. RecordManager stores each UID, its path group, timestamp, and a monotonic logical clock. The note path and embedding profile are part of indexed metadata, so changing either invalidates the native record hash. Search resolves winning notes against the live vault and hydrates their current content when needed.

The vector-store layer runs LangChain's default Markdown splitter once per note. It combines chunk texts across notes into embedding flushes of up to 512 chunks; an oversized note uses the existing bounded 512-chunk loop. Notes with no chunks require no embedding call. Transient validation checks that split counts, vectors, and profile agree before each note's atomic write. The SQLite worker does not import or rerun the splitter. The current native index schema does not persist the former custom `source_hash` or `chunk_count` fields.

Lexical search uses a contentless FTS5 index (`content=''`, `contentless_delete=1`, `unicode61`) over body and path text. The native index contract replaces the former custom get/list and availability lifecycle APIs; search remains SQL-backed.

Hybrid search combines SQLite BM25 lexical ranking and semantic ranking with reciprocal-rank fusion using rank constant 60. Semantic ranking uses each note's maximum chunk dot product. Related-note lookup scores normalized note centroids separately. Corpus computation stays in SQLite; vectors are not transferred to JavaScript for scoring.

## Index lifecycle

Manual **Update index**, **Rebuild index**, and **Stop** remain the indexing controls. The controller reserves one run watermark with RecordManager and sends notes to LangChain `index()` in document windows of up to 100, with cleanup disabled and `sourceIdKey: "path"` so note path metadata is the source identifier. Native index hashing decides whether each note is skipped or refreshed; an update refreshes an already tracked committed note. There is no second custom source-hash, reread, or prune lifecycle. The prepared note's UID, path, and logical-clock tick are registered atomically in the same transaction as its FTS and vector writes. Updates write timestamps strictly later than the reserved watermark. After every input succeeds, including an empty vault, the controller calls `index()` with an empty source to run full cleanup with page size 1,000; cleanup removes only records older than the watermark. RecordManager pages through stable UIDs in batches no larger than 1,000. Its existence check joins the recorded UID to the current note UID to handle the delete-before-record-delete gap, and UID-guarded deletion protects a newer same-path note from removal. If a committed source note is deleted before a successful follow-up Update, full cleanup removes its note, FTS, vector, and RecordManager state. Progress counts added, updated, skipped, and deleted native UIDs; visited counts note paths.

Cancellation messages are handled outside the SQL request queue. The worker yields during bounded SQL work and before commit, checking for cancellation. An abort rolls back the active note transaction; earlier completed note commits remain. Reset transactionally clears FTS, notes, vectors, RecordManager records, and the logical clock.

An indexing failure stops the run and skips full cleanup; cached lexical data remains available and Trama does not rewrite the failed note as lexical-only. The next manual update lets the native index lifecycle retry based on current content and metadata. Note edits made during a run wait for the next manual update. Query fallback to lexical search remains visible when semantic querying is unavailable. Embedding calls occur for note indexing and hybrid queries; related-note lookup uses SQLite centroid scoring and never calls a provider. Each indexing or query embedding request creates a fresh `OpenAIEmbeddings` instance with its own abort signal, so concurrent indexing and queries can be cancelled independently. Related-note results persist across restarts and refresh after an index update when the active note is opened.

## Worker and database lifecycle

The production worker processes SQL requests through a FIFO queue. RPC errors are bounded to `{name, message}`, and cancelled requests surface as `AbortError`. Bounded SQL work yields to check for cancellation before commit. Cancellation rolls back the active transaction and retains earlier completed note commits. Reset clears FTS, notes, vectors, RecordManager records, and the logical clock transactionally. Closing aborts active work, waits for transaction rollback, closes the database, and pauses the VFS non-destructively to release its storage pool. It acknowledges close before self-termination; the caller has a termination fallback. Settings changes await close before reopening the index. Each index instance owns its run callbacks so stale callbacks cannot affect a replacement instance.

The plugin awaits worker client initialization before publishing services or UI actions. Worker `error` and `messageerror` events reject initialization so the candidate client can close cleanly. Plugin loading, settings persistence, and configuration changes are serialized through one promise chain, with settings-updater work evaluated inside that chain. Disposed checks after awaits prevent stale clients or UI from appearing after unload; a client created by a pending run is closed if unload happens before that run finishes.

## Agent and privacy boundaries

Conversation history and turn attachments exist only for the current session or turn. Chat consumes native LangChain `BaseMessage.text` values and uses the experimental `agent.streamEvents` v3 stream for the proof of concept; final text is taken from `run.messages[].text` or `run.output`. A `wrapModelCall` middleware copies a bounded attachment block into the current `HumanMessage` only for that model request; the agent input and stored history keep the raw messages. Repeated tool calls in the same turn receive the current context, while a later different, unattached, failed, or cancelled turn cannot reuse it. This does not change the system prompt or trust boundary. Responses requests use plain-text `text.format`, `store: false`, and non-strict tool calling. Startup and settings loading work offline; provider access follows an explicit user action. Approved local private endpoints are guarded. Agent tools are read-only and return note links. Private attachment, provenance, cancellation, and partial-response behavior remain supported.

V1 has no shared cache or publication path, scheduled maintenance, automatic vault-event indexing, background indexing jobs, migrations, or legacy graph subsystem. Compatibility is limited to the Obsidian adapters needed to integrate with the plugin host.

## Verification and evidence

The batching change is covered by 12 focused tests, including embedding flush boundaries at 512 chunks and an oversized-note fixture. The fixture exercises provider batches of 511, 3, 512, and 1 chunks; tests also verify UID, vector, and FTS state across three notes. The final implementation reports 74 tests across 19 files, with test, build, type, SQLite, lint, and formatting checks passing.

The following counts describe the pre-batching middleware snapshot, not the current working tree.

As of 2026-10-11, the implementation work reports 18 test files and 67 tests, with `npm test`, build, strict-unused TypeScript, lint, SQLite verification, and formatting checks passing. Coverage includes native index skip/refresh, profile and path invalidation, stale-record cleanup including an empty vault, UID-safe deletion, both crash gaps, run watermark ordering and paging, failed-run retry, cancellation after completed note commits, reset rollback, and split/vector validation. Regression tests verify atomic note/UID writes, retained-source skips, and deletion cleanup. Attachment middleware tests verify that only the current model request receives its bounded attachment block, agent input/history remain raw, repeated tool calls receive that turn's attachment payload, and a different, unattached, failed, or cancelled turn cannot inherit old context. Existing tests cover production worker handling with real WASM, related-note persistence, provider request options, and the native agent stream. The chat work preserves native message text handling and covers experimental v3 event parsing, private attachments, provenance, cancellation, and partial failures. The cleanup removed obsolete legacy test and helper code, benchmark-only fixtures, and formatter exclusions. Twenty-four Markdown notes remained byte-identical.

The implementation has 4,549 source lines across 29 files, compared with 17,956 lines across 73 files before the rewrite, roughly 75% fewer lines. This middleware change added 13 lines to the previous 4,536-line/29-file version.

These counts describe repository checks, not device or live-provider validation.

A small workload used 24 committed Trama notes and 48 vectors. One pre-change sample reported 58.5 ms indexing and 8.9 ms query time; the native index version reported 162.9 ms indexing and 10.1 ms query time, with 20 results in both runs. Its SQLite database grew from 98,304 to 122,880 bytes. These single runs provide no speed claim, and this middleware change did not rerun the workload. The current built artifacts are `main.js` at 1,989,605 bytes (500,424 bytes gzip) and the worker at 14,118 bytes (4,785 bytes gzip). This task made no live provider calls; the earlier hello-only check does not validate agent tool execution. Full Obsidian integration on a device, desktop/mobile behavior, and a live agent tool roundtrip remain unverified.

Historical benchmark commands and reports describe earlier implementations. They are retained for context and do not define current V1 commands or performance guarantees.
