# 2026-09-25 — Let the database own relationships

Today I revisited the boundary between JavaScript and SQLite. The question is not whether one language is inherently faster. It is whether we keep rebuilding relationships in application memory that the database can maintain directly.

[[SQLite as an indexing engine]] gives the clearest summary: file access and Markdown preparation stay in JavaScript; coherent relational mutation belongs in SQL where appropriate.

The Worker boundary complicates the picture. A tiny query can still be expensive if the lifecycle sends it thousands of times. [[Worker transport has a cost]] and [[Bounded batches]] belong beside the database note rather than being treated as unrelated optimizations.

For the demo, I do not need to show implementation internals. But the notebook should contain enough substance for Voce to answer “Why not do everything in JavaScript?” without relying on a slogan. I will keep the wording about measured tradeoffs, not automatic speedups.
