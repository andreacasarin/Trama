# ADR: LangChain and SQLite note index

- Status: Accepted
- Date: 2026-10-09
- Updated: 2026-10-11

## Decision

Trama V1 is a complete rewrite built around LangChain's vector-store and default Markdown-splitting interfaces, OpenAI embeddings, a native LangChain agent, Zod-validated tools, and native call limits. Obsidian adapters provide host integration. The rewrite does not preserve the prior application's APIs, schemas, ranking, settings, caches, or test goldens, and adds no compatibility layer, migrations, shims, or parallel indexes.

SQLite is the source of indexed retrieval computation. The vector store stores note identity/path, embedding profile, chunk vectors, normalized note centroids, and lexical search data, but not raw Markdown bodies. LangChain's native `index()` lifecycle and SQLite RecordManager own content/metadata hashing, record UIDs, skip/refresh decisions, and stale cleanup. RecordManager stores each UID, path group, timestamp, and a monotonic logical clock; path and embedding profile are metadata, so changing either invalidates the native hash. The custom `source_hash` and `chunk_count` fields are not persisted. Hybrid search fuses SQLite BM25 lexical ranking with semantic ranking based on maximum chunk dot product, using reciprocal-rank fusion with rank constant 60. Related-note lookup scores normalized note centroids separately; its results persist across restarts and refresh after index updates when the active note is opened, without provider access. Embedding provider calls are limited to note indexing and hybrid queries; each request uses a fresh `OpenAIEmbeddings` instance and abort signal so concurrent indexing and queries can be cancelled independently. Winning note content is hydrated from the current vault.

Each vault receives a version-1 random 32-byte storage token, represented as 64 hexadecimal characters in `.trama/note-v1/identity.json`. The token determines its isolated OPFS database path, `trama-note-v2-<token>/notes.sqlite3`. The worker initializes that database before handling RPC. Reloading the identity preserves the vault's namespace; copying the identity file copies that namespace too. There is no shared-storage fallback.

Indexing is manual through Update and Rebuild. The controller reserves one run watermark with RecordManager and sends notes to native `index()` in document windows of up to 100, with cleanup disabled and `sourceIdKey: "path"` so the note path metadata is the source identifier. The adapter combines chunk texts across notes into embedding batches of up to 512; an oversized note uses the existing bounded 512-chunk loop. Native content/metadata hashing decides skips and refreshes; an update refreshes an already tracked committed note, with no custom hash, reread, or prune lifecycle. The prepared note's UID, path, and logical-clock tick are registered atomically in the same transaction as its FTS and vector writes. After all inputs succeed, including an empty vault, the controller calls `index()` on an empty source for full cleanup with page size 1,000. Updates use timestamps strictly later than the reserved watermark; cleanup deletes only records older than it. Stable UID paging is bounded to 1,000 records. The existence check matches the recorded UID to the current note UID for the delete-before-record-delete gap, and UID-guarded deletion cannot remove a newer note at the same path. If a committed source note is deleted before a successful follow-up Update, full cleanup removes its note, FTS, vector, and RecordManager state. A failed run stops and skips cleanup, leaving cached lexical data available; it does not rewrite the failed note as lexical-only. A later manual Update retries through the native lifecycle. Note edits made during a run are picked up on the next manual update. Query-time lexical fallback remains available when semantic retrieval fails.

The production worker processes SQL requests in FIFO order. Cancellation messages are handled outside the SQL request queue. Bounded SQL work yields for cancellation checks, and abort rolls back the active transaction while retaining earlier completed note commits. Reset transactionally clears FTS, notes, vectors, RecordManager records, and the logical clock.

Session history and turn attachments are ephemeral. Provider calls disable response storage. Startup and settings loading do not call providers. Tools are read-only and return note links. Worker initialization completes before UI/services are published; worker errors reject initialization and close the candidate. Plugin load, settings persistence, and configuration changes are serialized through one promise chain. Disposed checks after awaits prevent stale clients or UI after unload, and a client created by a pending run closes if unload happens before completion. Closing aborts active work, waits for rollback, closes the database, and pauses the VFS non-destructively to release its storage pool. Settings changes await close before reopening the index; each instance owns its run callbacks. Compatibility covers Obsidian adapters only. V1 excludes shared caches, publication, scheduled maintenance, automatic vault-event indexing, background jobs, migrations, and the legacy graph system.

## Context and rationale

The approved goal is a small, local V1 with a complete rewrite and no compatibility burden beyond Obsidian integration. Adopting LangChain's native index lifecycle minimizes custom hashing, skip/refresh, and stale cleanup policy. Registering the prepared note and its RecordManager UID/path/clock tick in the same transaction as FTS and vectors closes the write-before-native-update orphan gap. A custom SQLite adapter remains necessary to keep vector scoring and retrieval in SQLite and avoid persisting bounded vault text. Omitting raw note bodies from the index limits stored corpus content, while hydrating winners from the live vault keeps current note text authoritative. Per-vault identity and isolated storage keep each vault's index separate; stable identity reload preserves that namespace. Per-note atomic commits and bounded SQL work retain transactional cancellation boundaries; cross-note embedding batches reduce provider requests. The lexical fallback preserves a usable search path during query-time embedding or vector-query failures.

The choice of LangChain defaults, rank constant 60, and the centroid plus maximum-chunk scoring are approved V1 defaults; no separate rationale for tuning those individual values was supplied. They can be reconsidered with measured evidence without changing the privacy and storage boundaries above.

## Consequences

V1 has no automatic freshness guarantee: users explicitly update or rebuild the index. Note changes during an indexing run are handled by a later manual update. A failed run preserves prior lexical data and skips stale cleanup; query-time semantic failures can fall back to lexical search. Search results reflect indexed metadata and vectors but obtain displayed note content from the live vault. Old architecture notes and memory that describe query-time JavaScript centroids, cache publication, schedulers, generations, or migration machinery are historical context and do not override this decision.

## Reconsideration

Revisit this decision when product requirements call for automatic indexing, shared or published data, migration support, or when representative workload measurements justify changing the storage or ranking design. Any change must preserve explicit privacy boundaries and keep corpus computation bounded.
