# ADR: LangChain and SQLite note index

- Status: Accepted
- Date: 2026-10-09
- Updated: 2026-10-28

## Context

The proof of concept prioritizes reducing owned code through LangChain primitives while retaining SQLite computation and Obsidian integration. It is a pre-release rewrite: preserving old APIs, schemas, ranking, settings, caches, or test goldens is not a requirement.

## Decision

### Native indexing and SQL retrieval

The build embeds the SQLite module and WASM in the worker, then embeds that worker
in `main.js` using esbuild's binary and text loaders. A Blob-backed module worker
retains the existing RPC queue, cancellation, and OPFS storage identity. No runtime
asset downloads or alternative execution path are introduced. Source files stay
separate, and required licenses are embedded for standard community installation.

Keep exact cosine search as the current implementation. Do not add an approximate
index until representative end-to-end measurements justify a separate spike.
Keep one native double precision dot product for scoring and raw shard validation;
reuse the validated Float32 magnitude when normalizing bounded inputs. No parallel
precision modes, SIMD specialization, or search-engine dependency is introduced.

Use LangChain's vector-store interface, default Markdown splitter, native `index()` lifecycle, and a SQLite RecordManager. LangChain owns content/metadata hashing, record UIDs, unchanged-note skipping, record refresh, and stale cleanup. Do not retain a parallel custom source-hash, reread, or prune lifecycle, migration, or compatibility layer. Compatibility covers the Obsidian adapters only.

SQLite owns filtering, grouping, deduplication, ranking, and native vector scoring. Semantic scoring uses cosine similarity via dot products of normalized Float32 vectors, with double precision accumulation in Trama's small native SQL function. SQLite-Vector is no longer required. Validation uses the stored Float32 representation and the same arithmetic range; existing cache shards remain readable. Store note identity/path, embedding profile, chunk vectors, normalized note centroids, and contentless FTS data without raw Markdown bodies. Hydrate winning notes from the live vault. Hybrid search fuses body/path BM25 and maximum-chunk semantic ranking with reciprocal-rank fusion, using rank constant 60. Related-note lookup uses normalized centroids without provider access. LangChain defaults and these ranking values are approved V1 defaults; no separate tuning rationale was supplied. For the model-facing `vault_search` tool, retrieve ranked SQL candidates before hydrating live-vault notes. Iterate the full ranked SQL candidate pool, returning leading previews of up to 1,000 characters per hit, up to the requested result limit and within a 12,000-character serialized data cap. Stop before hydrating more candidates when the result limit is reached, or when the next preview would exceed the cap. Preserve ranking, canonical paths, and degradation status; report the full candidate-pool, hydrated, returned, and omitted counts. Missing notes are not hydrated. `hydratedCount` includes a successfully read candidate whose preview does not fit; `omittedCount` is candidate-pool count minus returned count; candidate count can exceed the requested result limit. Missing notes are skipped while counting successful live-vault hydration. This avoids hydrating lower-ranked candidates after the requested result count or serialized output cap is reached. Full reads remain available through `read_notes`.

The controller reserves a RecordManager run watermark, submits windows of up to 100 notes with cleanup disabled and `sourceIdKey: "path"`, then calls `index()` with an empty source and full cleanup after every input succeeds, including an empty vault. The adapter combines embeddings across notes into batches of up to 512 chunks; oversized notes use bounded batches too. Path and embedding profile are indexed metadata and affect the native hash.

Register each prepared note's UID, path, and logical-clock tick in the same SQLite transaction as its FTS and vectors. Timestamps must be strictly later than the reserved watermark; cleanup selects older records in stable UID pages of up to 1,000. Existence checks match the current note UID, and UID-guarded deletion cannot delete a newer note at the same path. A failed run stops and skips cleanup, retaining earlier committed notes and existing lexical data. Do not rewrite a failed note as lexical-only. Note changes during a run are picked up by a later successful update. Query-time semantic failure can fall back to lexical search.

### Vault and worker isolation

Each vault receives a version-1 random 32-byte token, encoded as 64 hexadecimal characters in `<storage-folder>/identity.json` (default `.trama/identity.json`). It selects the isolated OPFS database `trama-note-v2-<token>/notes.sqlite3`; copying the identity also copies the namespace. There is no shared-storage fallback.

Initialize the worker before publishing services or UI. Process SQL requests in FIFO order, handle cancellation messages outside that queue, and yield between bounded SQL steps and before commit. Cancellation rolls back the active transaction while retaining earlier note commits. Closing aborts active work, waits for rollback, closes the database, and pauses the VFS non-destructively. Settings changes await close before reopening; each index instance owns its callbacks.

Serialize plugin loading, settings persistence, and reconfiguration through one promise chain. Resolve current services for UI consumers after reconfiguration. Check disposal after awaits and close a candidate created during unload. External settings changes reload normalized `data.json`, apply runtime changes, and invalidate stale settings drafts. Closing the settings form preserves pending valid text edits and accepted confirmations; external replacement still invalidates them.

### Agent and privacy boundaries

Selecting Edit only prepares a composer draft; it leaves native history and the
visible conversation intact. Sending the revised prompt, after preflight and
nonempty-input validation, restores the native checkpoint immediately before that
prompt and removes the prompt and all later turns from the visible projection.
Keep only a per-user-turn reference to its preceding completed checkpoint; do not
reconstruct provider history from visible messages. Return the original prompt and
attachments to the composer for revision; cancelling the edit only clears this
draft. Sending a revision of the first prompt starts fresh
native history on the next send. Reject edits while a turn is running, and clear
checkpoint references on reset or when their visible turns are discarded.

Use a native LangChain agent, Zod-validated read-only tools, native message text, and the experimental v3 event stream for this proof of concept. Keep custom agent code limited to turn orchestration, provider-request context, budget enforcement, and UI projections; do not recreate native LangChain history, summarization, or tool execution policies. Keep per-session message history in LangGraph's native in-memory checkpointer rather than a manually maintained message array or persistent store; keep the visible transcript and cancellation state as separate UI/session projections. Replace the in-memory saver on reset so a new session cannot inherit writes from an older in-flight run. Promote a checkpoint only after a completed turn has visible answer text and no pending tool-call request. Set an application context budget through the Voce setting chat.contextWindowTokens (default 4,096), interpreted as approximate usable loaded context inclusive of reserved output. The counter is approximate; this setting does not change the provider's model context limit or LM Studio memory allocation. Use LangGraph's native summarization middleware to condense accumulated older conversation history when it approaches the configured budget, preserving the full current request, selected skill, and attached notes in the provider copy. If the request context itself exceeds the configured budget, stop with an actionable limit error rather than clipping it; report a provider context-overflow rejection distinctly. Preserve the code and message of Trama’s own `limit_exceeded` errors when wrapped in nested causes so these turns remain classified as incomplete; keep provider overflow classification distinct. Show compaction as a separate accessible status on the assistant turn: use a running state while a matching native summarization run is active, and mark it complete when the native summary message is observed and the following valid model call confirms its use. Do not treat a failed summarization or a turn that ends before this confirmation as completed compaction. Clear unfinished running state on cancellation or error, but preserve a successfully recorded compaction fact if a later turn step fails or is cancelled. The status explains that earlier conversation was condensed, details may be missing, the current request and recent context remain, and the visible transcript is unchanged; do not show the generated summary or append a notice to the answer. Separately, retain provider-returned reasoning summary deltas and final reasoning blocks on the assistant turn projection for a smaller, muted “Reasoning summary” display above the answer. Show only summary content returned through LangChain’s native reasoning stream or final reasoning blocks; a provider may return none. Preserve native LangChain AI message history for tool continuation, and do not manually append the display field to prompts. This adds no provider request parameter. Keep a turn-local retrieval ledger of successful attached-note and `read_notes` reads outside checkpointed history, and inject its source IDs, canonical paths, read counts, ranges, and truncation state as data in the current provider copy. Count ledger tokens in summarization and assembled-context limits. Subtract the fixed current request context and ledger from the native summarizer allowance, and account for request tools, skill, attachments, and ledger in the pre-provider-call budget guard. The ledger contains no note bodies, does not make search snippets or discovered links full reads, and does not claim model assessment or exhaustive completion. The existing Sources projection remains deduplicated by path and range; optional debugging reports anonymous source IDs and unique/repeated counts without note paths or content. Keep attachments and selected skill content turn-scoped in provider copies; human trust boundaries remain unchanged. Rely on LangGraph's default recursion limit; do not add custom model-call or tool-call counters or override the graph limit. This finite native graph-step bound preserves batching and native agent behavior without introducing application-specific count policy. Inject turn-scoped skill and attachment context through `wrapModelCall` into copied user messages only for provider requests; the visible invocation remains in history rather than the fetched skill body. Attachments remain available across tool calls in the same turn and cannot carry into later turns, including after failure or cancellation. Treat attached and retrieved note content as untrusted evidence on every turn, including turns without selected skills or attachments. For skill-based analysis, provide the selected skill and shared-note paths as source roots, inspect relevant links from both, and read known canonical target paths together with `read_notes`, supplying the source note as `sourcePath` when resolving paths relative to it. Honor the selected skill’s explicit source, depth, and retrieval limits while requesting evidence needed to answer and providing a cited answer before optional neighboring-note exploration. Broaden the read only within those limits when evidence is insufficient or the user asks. Do not crawl unrelated branches or automatically activate linked skills. Expose one `read_notes` tool for independent note reads, with a nonempty path array accepting exact vault-relative Markdown paths, unique visible titles, or complete wikilinks, and an optional nonempty `sourcePath` that resolves every supplied path relative to that source, including `.md` paths. Read paths in chunks of four with bounded concurrency, preserving input order and duplicates. Return one result per requested path so a failed note does not erase successful notes; batch-level success means the batch completed, while item errors remain per-item. Record canonical provenance and turn-local source progress only for successful notes, after the batch result is available. Cancellation stops later chunks and prevents publishing a partial batch as completed. Preserve full note content and the existing context-budget guard rather than silently clipping or omitting notes.

Use the OpenAI-compatible Responses API with plain-text `text.format`, `store: false`, and non-strict tool calling. Pass configured OpenAI-compatible chat and embedding base URLs through to the SDK without application-level host, IP, origin, path, or redirect filtering. Treat entering the URL as the user’s endpoint choice, with no separate origin-approval registry or approval step; users may include the path prefix required by their provider, while the existing /v1 defaults remain. Keep ordinary URL parsing, request cancellation, and embedding-vector validation. For embedding-cache identity, preserve cross-endpoint reuse for ordinary URLs; when a URL contains userinfo, a query, or a fragment, include a SHA-256 endpoint fingerprint to separate variants and strip those raw components from the serialized note profile. The fingerprint is a cache discriminator, not encryption. This removes duplicate endpoint filtering while leaving provider request handling to the SDK; it does not add authentication settings or promise support for every provider. Settings loading is offline; chat and search follow explicit actions, while eligible automatic indexing may call the embedding provider on cache misses. Each indexing or query embedding request uses a fresh `OpenAIEmbeddings` instance and abort signal so concurrent work cancels independently. Related-note scoring never calls a provider.

### Ephemeral Voce composer

Keep Voce drafting as ephemeral plain text in a `contenteditable="plaintext-only"` surface, using Obsidian's `AbstractInputSuggest` for inline note and skill suggestions. A small adapter handles text, caret, and token replacement; submitted Markdown renders in the transcript. Do not add a rich editor, CodeMirror layer, or persisted draft store just to support inline suggestions. This uses Obsidian's public suggestion UI while keeping the composer and session history lightweight.

## Rationale

Native indexing removes owned lifecycle policy. The atomic note/record write closes the write-before-record-update orphan gap without adding a second lifecycle. SQLite adapters preserve bounded corpus computation and avoid moving vectors to JavaScript. Omitting raw note bodies limits stored corpus content, while live-vault hydration keeps Markdown authoritative. Stable vault identity isolates local indexes across reloads. Native summarization middleware bounds accumulated working history without a custom message-trimming policy. Current request context remains intact, and confirmed history compaction is disclosed in a separate accessible turn status without changing the transcript. The ephemeral retrieval ledger preserves which sources were retrieved across condensation without adding a persisted source store or changing native graph recursion behavior; batch reads update it after the completed result, and per-note failures do not become evidence. Its token cost remains subject to the configured context budget. This records retrieval only, not model assessment or task completion. Keeping selected skills as explicit current-turn instructions and linked notes as untrusted evidence gives the agent useful source-relative context without granting reference notes instruction authority or crawling unrelated vault branches.

## Consequences

This is a simplification, not a claim of equivalent ranking or semantic quality. Failed runs can retain partial prior commits until a later successful update. The experimental agent stream and live-provider behavior require device-level validation. The legacy `MEMORY.md` described query-time JavaScript centroids and adaptive scheduler windows of 3→9→20 seconds with a 60-second deadline; the current table and maintenance ADRs record retained centroids and the current schedule. The earlier reason for those changes is not recorded. The “Approved V1 implementation contract” in `docs/work-brief-local-indexes-shared-cache.md` described section-aware structural chunks and a different ranking contract; that brief says the shared-cache direction was superseded by the V1 rewrite but does not preserve a reason for each change. Its schema 16/protocol 13 and `MEMORY.md`'s schema 6 and coupled runtime identity v9 are historical version notes, not current compatibility claims. These older details are provenance, not current behavior or rationale.

Retain the existing 5a clock SQL; do not adopt `UPDATE RETURNING`. In the 2026-10-19 profile-off comparison, a 3,000-note candidate was tested with two warmups per side and 12 balanced rounds across three sessions. It beat both controls in only 4/12 rounds for no-op and delete, and its paired median gains (0.29% and 2.45%) failed the predeclared gate for both operations. This result was offline-validated from preserved browser output, not a clean successful runner result: the original identity guard failed on workspace-path comments in emitted bundles, and original bundle hashes were not retained. Offline checks found equal input closures and rebuilt workload bytes after only that comment normalization; executable-byte differences were rejected. No rerun occurred, and this evidence does not establish behavioral equivalence.

## Reconsideration

Revisit native defaults and ranking with representative quality and performance evidence. Revisit the rewrite boundary if compatibility or migration becomes a product requirement. Preserve bounded SQL computation, vault isolation, and privacy boundaries.
